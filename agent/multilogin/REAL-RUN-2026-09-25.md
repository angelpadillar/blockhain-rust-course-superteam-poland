## Live proof attempts and the blocker

Command shape (mirrored locally under `.browser-jobs/`):

```sh
docker compose run --rm --no-deps -T \
  -v /opt/buena-multilogin-orchestrator/src:/app/src:ro \
  -v /opt/buena-multilogin-orchestrator/job-runner.mjs:/app/job-runner.mjs:ro \
  --entrypoint node worker job-runner.mjs /data/proof-job.json \
  --data /data/account-pilot --config config.vps.json --accounts /data/accounts.json \
  --token-file /data/automation-token --provider fireworks --key-file /data/fireworks-api-key --no-notify
```

Both attempts reached `PROFILE_READY` and stopped at profile start with
`multilogin_http_403`. The launcher log shows the real cause:

- every listed profile's premium proxy fails its IP check:
  `socks connect tcp 51.195.126.60:1080->proxy.multilogin.com:443: unknown error
  connection not allowed by ruleset` → profile status `validate_proxy_error`
  (`couldn't get proxy connection ip data`) → start returns HTTP 400;
- the automatic one-proxy rotation the kernel is allowed to make cannot happen
  because the cloud proxy endpoint returns HTTP 403:
  `api.multilogin.com/proxynm/connection_url` → `multilogin_http_403`.
  Workspace reads (`/workspace/folders`) still succeed with the same token.

This is an external Multilogin proxy/subscription condition, not an orchestrator
defect: a successful canary run on the same workspace completed on
2026-09-23T21:40Z. The orchestrator handled it deterministically — a precise
`FAILED` reason, durable transitions, no secret in any log, no profile left
running, no retry loop.
