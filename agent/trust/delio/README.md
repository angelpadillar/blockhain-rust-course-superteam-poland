# Delio checkout-quote pilot

This milestone prepares one reviewable grocery checkout quote and, when its evidence is verified, demonstrates exact authorization in local LiteSVM. **It cannot place a Delio order or make a payment.** The previous fictional gifting demo is preserved separately.

## Run and account ownership

From the experiment workspace:

```sh
node trust-layer/delio/server.mjs
```

The default UI binds **http://127.0.0.1:4319** on the local Mac. `DELIO_PORT` and `DELIO_PRIVATE_DIR` are operator-side settings. The server creates its private directory with restrictive permissions, a single-owner lock and `operator.json` when absent. That file holds the local admission code, customer/account mapping, delivery commitment and allowances. Read the code privately; never paste it into source, a model prompt, screenshot or public report. The admission code opens this local workspace; it is neither a Delio credential nor wallet authentication.

Use a single owner for each merchant account. The adapter's fixed SSH transport targets the private `buena-delio-worker` container on the configured Tailscale VPS; it accepts finite operations rather than caller-supplied shell commands, URLs or scripts. The isolated worker profile is stored under `/data/buena-delio/state` with a single-owner lock. Its profile, login/OTP and full delivery details stay private; the UI does not attach to the user's selected browser. Local HTTP ownership, worker profile ownership and authenticated merchant access are distinct checks. The worker service and UI transport are validated for reporting current access blockers; live cart and quote capabilities remain disabled.

An operator may set `DELIO_SSH_CONTROL_PATH` to a private socket for an already authenticated, short-lived SSH connection. This trusted server-side setting avoids repeated signing prompts; it is not accepted through HTTP or worker payloads and does not alter global SSH configuration. Connection reuse does not establish merchant login or permit concurrent profile owners.

The devnet payment rail is configured server-side only: `PRIVY_APP_ID` (or `privyAppId` in `operator.json`) enables the wallet UI, `DELIO_SOLANA_RPC` overrides the devnet RPC endpoint, `DELIO_SOL_PLN_RATE`/`DELIO_USD_PLN_RATE` set the conversion rates used to price intents, and `DELIO_PAY_EXECUTOR` names an optional local command invoked once with the funded order path after an on-chain-verified payment. The treasury keypair is generated once into `private/payments/treasury.json` (mode `0600`) and never leaves the server; the Privy **app secret is not used anywhere** — the on-chain transaction itself is the payment proof. Paying funds a `FUNDED` order record; it is not an escrow, no program holds the funds, and a confirmed transfer does not place a merchant order. Every funded order carries `settlement.usdcMinor` — the executor's USDC-denominated amount, converted from whatever the customer paid (SOL settles at its USD value under the configured rates, USDC settles 1:1). When `DELIO_SETTLEMENT_USDC_DEST` (or `settlementUsdcDestination` in `operator.json`) names a Solana address — e.g. an Altitude deposit address — the treasury also **delivers** that amount on-chain as real USDC to the destination's associated token account before dispatch: the conversion is custodial, funded by the treasury's USDC float, and the settlement transaction carries the intent's reference account for auditability. Delivery status (`pending`/`submitted`/`settled`/`insufficient_float`/`failed`) gates the executor — an unsettled order stays `execution_pending` and retries on the next status check, so topping up the float unblocks it. Without a destination, settlement stays `accounted` (verified accounting only). Devnet has no SOL↔USDC swap venue, so "conversion" means the rail fronts USDC against received SOL; on mainnet the same seam could become a real swap.

The worker's isolated [manual desktop](http://100.121.5.10:6094/vnc.html) is available over the private Tailscale network while the worker is explicitly active, with a five-minute idle limit. Its password is stored locally in [desktop-password.txt](/Users/buena/Documents/ChatGPT/typesafe-ai-experiment/trust-layer/delio/private/desktop-password.txt), with mode `0600`; this credential file is excluded from source mirrors and public evidence. Enter it privately. The desktop HTTP response and password-protected RFB handshake were validated. The assisted Delio account session was observed separately. Revalidate that session and delivery confirmation before cart work; desktop availability alone proves neither.

The generated delivery commitment is not evidence that Delio accepts the user's address. A live quote must bind the privately configured destination to fresh, owned worker observations. Do not publish delivery details or use a new browser/profile as a shortcut around uncertain prior state.

Defaults allow one concurrent worker, five live quote attempts, twelve cart updates, zero model calls and 300 seconds of total worker allowance, with a 30-second operation limit. Counters and pending intent persist. A stopped or interrupted worker requires review; restarting does not reset permission. `SIGUSR2` invokes the operator stop switch; shutdown signals stop work and close the HTTP server. A stale ownership lock requires checking that its process has ended before removal.

Clients cannot submit prices, totals, delivery addresses, coupon claims or arbitrary account IDs as trusted quote state. Cart and authorization requests carry the current version; quote authorization also carries the exact quote ID. Server configuration supplies the delivery commitment and optional coupon. Required checkout components include items, mandatory fees, deposits, discounts and merchant total; absent values are not silently replaced with zero.

## Meaning of the local Solana proof

The authorizer requires a fresh verified PLN quote, matching customer/account ownership, exact evidence observations and a funded local demo vault. It commits the merchant/account, full item lines, recipient/delivery commitment, full quote and evidence hashes. JavaScript recomputes both the **602 canonical bytes** and the Rust digest before authorization. The resulting receipt includes real locally executed transaction signatures, logs, decoded account state and the SBF hash.

The existing narrow bridge stores the **aggregate total** as its campaign item-subtotal field. Detailed merchant line items, deposits, fees, discount and the separate Buena fee are bound in `quoteHash`; they are not individually represented in the bridge's economic fields. Do not present this as field-by-field checkout validation by Solana. The server validates those merchant observations before requesting the local transaction.

The chain backend is ephemeral **LiteSVM**, with demo signers and demo tokens, not a connected wallet, devnet/mainnet deployment, real escrow or real FX. The child closes after its authorization proof is captured. This is retained evidence of local authorization, not a persistent spendable authorization for a later worker. This pilot never consumes the mandate for a live order, authenticates a live payment, records a real purchase or settles funds.
