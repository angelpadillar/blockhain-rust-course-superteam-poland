**19 September implementation update:** `../integrated/README.md` describes the new working local path. It independently matches the Rust encoding, executes signed transactions against the compiled program in LiteSVM, gates a browser-driven merchant fixture on confirmed account state and verifies its result. The rest of this document preserves the earlier audit; its statements that the demonstration is disconnected describe the older `demo/` UI, which remains separate. No production wallet or live-payment integration is implied.

Read-only audit of `/Users/buena/Code/blockchain-rust-superteam-poland`, 2026-09-17. No credentials, private run artifacts, live merchant calls or chain transactions were read or performed. The original project was not edited for this audit.

The repository contains a CLI/Anchor application. Its package manifests and source inventory show no React/Next/Vite UI or browser-wallet client. The existing approval UX is terminal-based; `scripts/fulfillment-chain.ts` uses `@anchor-lang/core` with a local Keypair-backed `AnchorProvider`. The new local demo is a UI prototype, not an existing authenticated wallet screen.

The original nine LiteSVM tests cover happy-path settlement, exact quote/payment-auth/purchase transitions, mismatch rejection, sender authorization, zero hashes, cancellation, in-flight-payment recovery and wrong mint. `agent/tests/policy.test.ts` covers quote/fee/cap validation, defaults, one-attempt status, payment-surface policy, fresh OTP scope and secret redaction. These were inspected, not rerun by this audit.

The new Rust candidate additionally introduces a one-use sender mandate, a designated executor and program-recomputed exact terms digest. It binds merchant/spec/recipient commitments, currency, price/escrow caps and expiry; the executor may approve a quote within those signed terms and atomically consume the mandate before an attempt. This is distinct from asking the sender to sign every individual quote. The local demo currently illustrates exact quote review and consumption; its JSON evidence hash is not byte-compatible with that Rust digest and no delegated or wallet signature is claimed.

A concrete next integration is a typed prepared-quote receipt from the browser worker, independently checked against the gift specification and merchant checkout, followed by the exact-term approval/mandate service, then a separate one-attempt fulfillment executor. The evidence library can link the reviewed quote screenshot, explicit approval boundary and merchant confirmation while keeping payment credentials, recipient PII and OTPs out of public artifacts.
