# Fast browser agent: architecture and implementation record

Implementation update, later on 17 September 2026: the isolated [v3](experimental/browser-runtime-v3/CLI.md) and [v4](experimental/browser-runtime-v4/README.md) candidates now implement native operations, an inexpensive OpenRouter planner, Jev ambiguity selection and a bounded continuous workflow. [V3 results](benchmarks/browser-runtime-v3/REPORT.md) separate executor overhead, real planning, guidance and incomplete billing. The design below predates those implementations; proposed workflow memory, broader native controls and automatic replanning remain future work. The deployed Glovo baseline is unchanged.

Saved 17 September 2026 in response to the request for a faster, more general browser agent. This is the next implementation design, not a claim that the new runtime or general planner has been built or benchmarked. The existing baseline and both measured candidates remain unchanged.

The recommendation is a hybrid browser agent: execute familiar, verified operations in code; ask Jev to resolve semantic ambiguity; use a reasoning/text model for unfamiliar goals, novel text and unfamiliar recovery. Convert successful procedures into parameterized workflows that rebind to the current page. Optimize time and total cost per verified completion.

## What the evidence says

The three successful baseline traces from the retained speed experiment followed the same eight browser steps, with seven Jev requests and one separately authorized age confirmation. Median navigation time was 14.022 s. Median model time was 2.077 s; browser/runtime residual was 11.411 s; journal time was 0.535 s. These are independently calculated component medians, not a partition of a single median run.

Reconstruction from event timestamps assigns a median 9.572 s to post-action observation/readiness and about 0.398 s to execution/revalidation. Readiness includes DOM reads, polling, rendering and actual website work; it is not all removable overhead. Eight nonterminal observations, including the initial one, require 700 ms stability each: a 5.6 s implementation floor within the recorded timing, not an additional duration or an achievable saving estimate.

Subtracting each successful trace's entire model time gives 12.761 s, 11.610 s and 11.946 s. Their median is 11.946 s, versus 14.022 s measured: an idealized 14.8% elapsed reduction, or 1.17× speed, with every other event held fixed. Faster inference alone cannot produce a large improvement on this route. Changing the workflow can change other costs too, so this is a fixed-trace counterfactual, not a universal bound.

The first richer prompt failed despite a present submit action. The second candidate restored that decision, then met a site error. Neither activated its faster readiness or stale recovery before stopping. Preserve these failures; do not use them as evidence that the proposed optimizations succeed. [Full measured report](benchmarks/navigation-speed-v2/REPORT.md)

## Runtime and decision layers

1. **Task compiler.** Normalize the request into a typed goal, allowed operations, data supplied by the user, stopping point and independently checkable outcomes. Structured requests and known templates can use code; unfamiliar prose can use a planner once, with later calls only for materially new planning. A closed-set Jev router cannot invent arbitrary field strings or plans. Our current service does not yet have an automatic general planner/writer API configured.
2. **Browser worker.** Keep Playwright and the decision runtime together on the server, as they already are. Capture relevant HTML/ARIA controls together, retain real element identity, validate the chosen target and use native input. Consolidate repeated full-page observations and measure protocol calls before replacing Playwright with raw CDP. Browser launch was only tens to hundreds of milliseconds in this experiment; reusing it is operationally useful but not the main measured bottleneck. Process one operation at a time per account.
3. **Verified operations.** Expose `search(query)`, `openObservedResult(identity)`, `setFilter(value)` and `readDetails()` on top of click/fill/press/select/scroll. Every operation has a precondition, bounded native actions and a postcondition. For a known Enter-submitted search, fill and submit belong to one operation; code still validates each input and journals before dispatch. Live-search and autocomplete widgets require their own behavior, rather than pressing Enter universally. Stop a sequence when its expected state does not appear.
4. **Decision routing.** If exactly one currently observed permitted control satisfies a validated identity/rule, execute in code. If several candidates need interpretation, ask Jev one focused question over those candidates. If the page/workflow is unfamiliar or progress repeatedly fails, refresh/replan within a bounded budget. A larger model is not necessary for routine stale-element retries. Batched questions are independent; operation-specific target questions need explicit conditional premises and compatibility validation.
5. **Workflow memory.** Store semantic procedures, parameter slots, supported page conditions, verification rules, adapter version and success/failure evidence. Rebind each step to fresh elements; never replay old coordinates, snapshot refs or unchecked selectors. A verified example is a proposed reusable workflow, not proof of generality. Test changed item names and layouts before promoting it. Do not put benchmark answer URLs or private account data into shared memory.
6. **Verifier and effect controls.** Verify observable state after meaningful operations and at completion. Preserve the existing navigation-only task limits and durable action records. Model confidence or DONE cannot authorize a purchase or prove completion. Preparation and payment submission remain separate operations with separate authorization and outcome reconciliation; uncertain side effects are not replayed.

## Readiness by operation

Replace page-wide quiet time with conditions relevant to the operation. A fill needs evidence that the correct field contains the intended text. A submit needs fresh results associated with that query, an explicit empty result, or a known failure. Opening a product needs rendered details for that product. Unrelated animations should not restart the wait; unrelated new links should not satisfy it. Use page events/mutation observation plus bounded checks of DOM properties; property changes are not all observable through mutation events. Keep a deadline and a conservative fallback for unsupported cases.

Register observation before executing to avoid missed transitions. Read a current snapshot after the event, then verify its semantics. Reuse only decisions whose relevant target/document/form state remains valid. A stale decision rejected before dispatch can refresh/reselect. A timeout after a click or submission needs reconciliation, not blind replay. Native actionability checks still apply.

For the known Glovo route, a parameterized workflow would search for a merchant, open a current matching result, search for the requested product, ask Jev for a relevant category if necessary, resume the selected navigation intent after the already authorized gate, and independently verify the product. The repeated category choice and separate fill/submit decisions are candidates for removal. This is a proposed procedure, not a new measured call count or speed result.

## Generality and benchmark integrity

The existing adapter does control a browser, but it is specialized. `instruction` is recorded rather than directly driving the model request. Merchant/product strings supply queries; `targetUrl` also controls stages and excludes other store/product links. The existing experiment therefore tests a configured route, not blind instruction following on an unknown website.

For new agent benchmarks, the policy receives only the user's request, allowed scope and starting page. Put expected destination URLs/IDs in a separate verifier. Where a test's safety guard needs exact identifiers, the guard may hold them but must not use them to rank or prefilter the policy's candidate actions. Known destination URLs may be useful in a separately labeled production shortcut mode, but do not use them to skip a homepage-to-product navigation benchmark.

Report two workloads separately: unfamiliar tasks with no stored procedure, and repeated tasks using validated workflows. Include workflow discovery/planning cost, runtime inference, failed attempts and recovery. Warm workflow speed must not be reported as unseen-site agent performance. Supported official merchant APIs can be a future production option; any API execution must be measured separately from browser interaction.

## Concrete next build and experiment

Build an isolated `experimental/browser-runtime-v3/` prototype with four interfaces: observation, native execution, operation-specific readiness, and independent verification. Its first complete operation is search-and-open from an observed search control. Keep the successful Glovo adapter as a regression reference.

First measure execution in a resettable local store fixture with the exact same prescribed actions and zero model calls. Compare the baseline-style observation/stability loop with the operation-based loop. Vary immediate and delayed results, live versus Enter search, duplicate labels, node replacement, unrelated animation, empty results and product-title delay. Count browser protocol calls, observations, dispatched actions, readiness time, journal time and verified completion. This measures executor overhead without attributing merchant outages to the model. A deterministic reference using known fixture actions provides a lower bound for that fixture, not general agent performance.

Then freeze the runtime and run a held-out task set with varied goals and layouts. Compare existing stepwise Jev decisions against operation routing with Jev only for ambiguity, under the same provider and task limits. Keep the verifier's answer data inaccessible to both policies. Test known workflows and unfamiliar tasks separately. A small initial fixed suite can use ten held-out tasks and three repetitions per arm; publish every result, and report median/range rather than a stable p95 claim at that size.

Only after those checks should the frozen candidate return to live Glovo and additional supported sites. Include page load and final verification in the primary clock; show browser/session setup separately. Do not claim an improvement until completed-task time falls without losing completion in the compared suite. Set the speed objective after measuring the executor's achievable floor instead of promising subsecond website completion.

## Primary sources checked for this design

- [TypeSafe build guide](https://docs.typesafe.ai/concepts/how-to-build-with-system-one): code owns control flow and deterministic work; structured model judgments supply semantic decisions.
- [TypeSafe state](https://docs.typesafe.ai/concepts/state) and [fan-out](https://docs.typesafe.ai/patterns/fan-out): text/JSON observations and independently evaluated questions; no dependency between simultaneous answers.
- [TypeSafe function calling](https://docs.typesafe.ai/cookbooks/function_calling): typed function selection with closed-set parameters; it does not make arbitrary free-text generation a Choice operation.
- [Playwright actionability](https://playwright.dev/docs/actionability): visibility, stability, enabled state and event-receiving checks before input. Actionability is distinct from application-level result verification.
- [Jev Ultrafast measurements at the reviewed revision](https://github.com/browser-use/jev-ultrafast/blob/452c1ad2dd628008f1d5608f28158d76e49e6cc0/docs/performance.md): the repository reports three successful paired flight runs per arm, median 9.450 to 7.092 s, with median protocol calls 1,092 to 101. This is their task/profile and timing boundary; initial navigation and fresh independent post-run verification are excluded. It supports investigating browser round trips and readiness, but is not our speedup or a universal result. Its reader also has documented gaps in frames, shadow roots and other controls.
