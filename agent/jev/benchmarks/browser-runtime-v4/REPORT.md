# Browser runtime v4 — continuous workflow experiment

Measured on 2026-09-17. The paid cohort completed **6/6 supplied structured plans**, with a median measured task time of **0.643 seconds**, but **0/6 plans generated from prose**. This distinction matters: the browser executor supported these two-operation tasks, while the initial planner did not reliably express them. Every failed task and its model cost is retained. The planner has since been corrected, but both attempted rerun launches stopped at 1Password authorization before any API request. **The corrected planner has no live full-workflow result.**

V4 accepts at most four `search_and_open` or `open_link` operations. One optional OpenRouter call compiles prose into those operations. A local worker executes the plan, takes fresh DOM observations and calls Jev only for semantic ambiguity or a nonliteral context constraint. Supplied plans omit the planning call. Each operation requires a changed URL and a visible exact heading; independent task verification remains separate. This is a bounded browsing prototype, not general arbitrary browser control or a shopping transaction system.

**Workload and verification.** Three synthetic cases each run twice per arm: merchant search followed by item search; selection of a merchant in “the district for creative studio work” followed by item search; and opening an already visible contextual merchant link followed by item search with a delayed detail heading. Duplicate merchants can expose the same item title, so a matching heading alone cannot establish success. Every reported fixture success passed all five external checks: local origin, exact private detail route, visible exact item title, correct merchant and correct district. Destination route IDs remain in the fixture verifier, outside the planner and chooser inputs. Both paid arms use the same executor and real Jev guide. The within-case order is prompt/structured, then structured/prompt; this is counterbalanced, not randomized.

The recorded plans explain concrete failures. In four attempts, the planner copied the preceding merchant name into the product's result-context constraint. That name was not an ancestor label of the product result, and the chooser abstained; the current adapter records this as `chooser_invalid_ref`, a reason that also covers a valid `none` answer. In two direct-link cases, the planner chose `search_and_open` for the initial “open” clause, although that fixture offers a link and no initial search field; execution stopped at `no_search_control`. The guard did not waive these constraints to force completion. This cohort provides no successful prompt time or successful-task speedup ratio.

The first cohort used 16 model calls, 6,324 input / 1,064 output tokens and **$0.000621448** including failures. The structured arm's all-attempt cost per verified success was $0.000013272. The prompt arm has no cost-per-success estimate because it had no verified successes. All attempted calls received responses with usage; there is no unknown-cost call in this cohort.

The corrected planner (`readonly-workflow-2`) clarifies that the previous merchant is already the current page, limits context to constraints belonging to the current step, and chooses open versus search separately for each clause. It adds two generic examples with names absent from the fixtures. The executor, search behavior and provider client are unchanged from the paid cohort. This is development tuning after observing these cases, not a held-out evaluation. No successful outcome or timing is attributed to this correction; the saved paid source snapshot contains the original planner.

**Executor-only cohort — six tasks, no model calls.** The supplied public plans used a declared deterministic semantic oracle, including the mapping from creative-studio-work wording to “Studio district.” All six tasks passed the independent verifier. Median measured task time was **0.357 seconds [0.299–0.879]**; median runtime time was 0.318 seconds. The last two tasks deliberately delayed their destination heading by 650 ms. These measurements establish local execution behavior with a supplied plan and oracle, not model reasoning accuracy. **Timing and billing boundaries.** `totalMs` includes initial navigation, overlapping planning, runtime, independent verification, settlement of pending provider requests and the first durable completion write. Browser launch, context setup, cleanup and the final timing-metadata write are excluded. Initial receipt and batch writes are also excluded. Planning overlaps navigation; condition waits overlap DOM observation; journal time overlaps execution. These components must not be added as independent phases. Each task receives a fresh context in a shared browser, which does not guarantee cold operating-system or network caches.

The default planner is `google/gemini-2.5-flash-lite`, routed to `google-ai-studio` without provider fallback. The first paid cohort reported that exact model and Google AI Studio for every planner response; every Jev response reported `jev-1.13.0` for requested alias `jev-latest`. OpenRouter amounts are returned account charges; Jev amounts are estimates using $0.042 per million input tokens and zero output charge. Independent recomputation checked each ledger's call count, token sums and costs, including failed tasks; the OpenRouter charges in this text-only cohort also match recorded tokens at $0.10/M input and $0.40/M output. No image calls occurred. Screenshot guidance remains a separate explicit option, not a feature measured here.

Each task permits at most six model calls. The $0.01/task and $0.10/batch values are known-spend stop thresholds, not hard guarantees about charges for requests already sent. Missing provider usage stops subsequent tasks rather than being priced at zero.

Across the paid fixture cohort and the separate interrupted Wikipedia attempt, **17 recorded model requests** account for **6,591 input / 1,119 output tokens** and **$0.000670148** in reported charges plus Jev estimates. This includes the failed fixture tasks. It excludes earlier v3/Glovo experiments, browser infrastructure and unrelated account use. The offline oracle, model-free smoke and three setup failures add no API requests to this scope.

The fixture results do not establish performance on unseen sites, availability during merchant outages, arbitrary forms, authentication, visual-only controls or purchases. No Glovo retest or deployment occurred. V3 and the original Glovo evidence remain unchanged; their measured times are not comparison arms in this report. A useful next evaluation freezes the planner and runs new wording and new page layouts, retaining every failure and independent destination checks.
